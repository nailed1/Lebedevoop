## Структура проекта: шахматный движок + GUI

### Общая архитектура (два слоя)

Проект разделён на два независимых слоя:

1. **Бэкенд** — C++, компилируется в разделяемую библиотеку `libchess.dylib`
2. **Фронтенд** — Python (`chess_gui.py`), загружает библиотеку через `ctypes`

Связь между ними — тонкий C-совместимый API (`chess_bridge.cpp`).

---

### Слой C++ — файлы и классы

#### `figures.h` / `figures.cpp` — иерархия фигур

Главный OOP-узел проекта. Абстрактный базовый класс `Figure`, от него наследуют 6 конкретных классов:

```
Figure  (abstract)
├── King
├── Queen
├── Rook
├── Bishop
├── Knight
└── Pawn
```

**`Figure`** хранит три поля: `color` (Color::White / Color::Black), `type` (PieceType::E), `hasMoved` (для рокировки и двойного хода пешки).

Чистые виртуальные методы, которые обязан реализовать каждый наследник:
- `getSymbol()` — символ для отображения ('K', 'k', 'Q', 'q', …)
- `clone()` — виртуальный конструктор копирования (создаёт копию, зная только `Figure*`)
- `getMaterialValue()` — вес фигуры в сантипешках (пешка=100, конь/слон=300, ладья=500, ферзь=900)
- `getPositionalValue(row, col)` — бонус за позицию (таблица PST)
- `getPseudoMoves(r, c, table)` — список клеток куда фигура может пойти без проверки шаха

**Фабричный метод** `Figure::create(type, color)` — единственное место, где создаются объекты фигур. Возвращает `new King(c)`, `new Queen(c)` и т.д. по типу.

**Почему `clone()`**: при поиске ходов нужно копировать всю доску. Но у нас есть только `Figure*`, а не конкретный тип. Виртуальный `clone()` позволяет сделать правильную копию, не зная точный класс объекта — это паттерн "виртуальный конструктор".

**Почему виртуальный деструктор**: при `delete Figure*` без виртуального деструктора вызовется только деструктор `Figure`, а деструктор наследника — нет. Это UB и утечка памяти.

#### `cell.h` — клетка доски

`Cell` хранит координаты (`row`, `col`) и указатель `Figure*`. **Cell не владеет фигурой** — `delete` она не вызывает. Всем управляет `Table`. Это намеренное решение: метод `wouldLeaveInCheck` временно переставляет указатели (без удаления фигур), что было бы невозможно при владении в `Cell`.

---

#### `table.h` / `table.cpp` — доска

`Table` — центральный класс, управляет всем состоянием игры.

Поля:
- `Cell cells[8][8]` — единственный владелец всех `Figure*` (отмечено `mutable`: нужно для `wouldLeaveInCheck`, который технически const, но временно двигает фигуры)
- `Color::E currentTurn` — чья очередь
- `Position enPassantTarget` — цель взятия на проходе, (-1,-1) если недоступно
- `bool gameOver`, `Color::E winner`, `bool isDraw`

Ключевые методы:
- **Конструктор копирования** — делает глубокую копию: для каждой из 64 клеток вызывает `figure->clone()`. Нужно для AI и MateSearcher, которые перебирают ходы, не меняя исходную позицию.
- `getValidMoves(r, c)` — берёт псевдолегальные ходы фигуры, отфильтровывает те, что оставляют короля под шахом
- `makeMove(fr, fc, tr, tc, promotion)` — выполняет ход, обрабатывает рокировку, взятие на проходе, превращение пешки, переключает ход, проверяет мат/пат
- `wouldLeaveInCheck(...)` — временно делает ход, проверяет шах, откатывает (const-метод через `mutable`)
- `isSquareAttacked(r, c, byColor)` — проверяет, атакует ли цвет `byColor` клетку

#### `ai.h` / `ai.cpp` — искусственный интеллект

Класс `AI` реализует поиск лучшего хода через **минимакс с альфа-бета отсечением**.

`struct Move` — просто структура с полями `fr, fc, tr, tc, promotion`.

`AI(depth)` — глубина поиска, обычно 3–4.

`getBestMove(board, color)` — запускает минимакс, возвращает лучший `Move`.

`minimax(table, depth, alpha, beta)` — рекурсивный поиск. Белые максимизируют, чёрные минимизируют оценку. Альфа-бета отсекает ветки, которые заведомо хуже уже найденного.

`evaluate(table)` — статическая оценка позиции: сумма `(materialValue + positionalValue)` для всех белых фигур минус то же для чёрных.

`collectMoves` — собирает все ходы цвета, сортирует взятия вперёд (эвристика: взятия — лучшие кандидаты, их рассмотрение первыми улучшает отсечение). Вместо лямбды используется структура `CaptureSorter` с `operator()` — функтор.

---

#### `mate_searcher.h` / `mate_searcher.cpp` — решатель задач на мат

Все методы статические — экземпляр не нужен.

Логика принципиально отличается от AI: здесь нужно найти ход, который ведёт к мату **при любом ответе** соперника.

- `mateIn1(t, out)` — перебирает все ходы белых, ищет тот, после которого `isGameOver() && winner == White`
- `mateIn2(t, out)` — для каждого хода белых проверяет: для **всех** ответов чёрных существует mateIn1? Если да — ход найден
- `mateIn3(t, out)` — аналогично: для всех ответов чёрных — mateIn2?
- `findMatingMove(board, maxDepth)` — пробует mateIn1, потом mateIn2, потом mateIn3
- `loadPosition(table, filename)` — парсит текстовый файл с позицией (формат: `White:\nKE1\nQA4\nBlack:\nKD8`)
- `solvePuzzle(inputFile, outputFile)` — загружает, ищет мат, пишет решение в файл

#### `chess_bridge.cpp` — C-совместимый слой

`extern "C"` блок отключает name mangling — иначе Python через `ctypes` не нашёл бы функции (C++ компилятор искажает имена для поддержки перегрузок).

Паттерн **opaque handle**: Python получает `Table*` как `void*` (просто адрес в памяти) и передаёт его обратно при каждом вызове. Python не знает внутреннего устройства `Table` — только адрес.

Схема вызова: `chess_gui.py` → `ctypes.CDLL("libchess.dylib")` → `chess_bridge.cpp` → `Table` / `AI` / `MateSearcher`

### Слой Python — `chess_gui.py`

Загружает `libchess.dylib` через `ctypes`, регистрирует типы аргументов/возвращаемых значений для каждой функции (без этого ctypes не знает, как преобразовывать типы).

**`ChessEngine`** — тонкая Python-обёртка над C++ объектом. Создаёт `Table` через `chess_create()`, при удалении вызывает `chess_destroy()`. Методы: `board()`, `turn()`, `valid_moves(r,c)`, `make_move(...)`, `get_best_move(color, depth)`, `find_mate_move(max_depth)`, `load_position(file)`.

**Классы UI**:
- `StartScreen` — начальный экран выбора режима
- `GameModeScreen` — выбор (Игрок vs Игрок, Игрок vs ИИ, ИИ vs ИИ)
- `ChessGUI` — основная игра, поддерживает все 4 режима. Правая панель — история ходов, сохраняется в `history/` при завершении партии
- `PuzzleSelector` — список 4 задач
- `PuzzleGUI` — режим задачи: пользователь за чёрных, ИИ за белых. В потоке `threading.Thread` ИИ сначала ищет форсированный мат, иначе — обычный минимакс
- `BoardCanvas` — отрисовка доски на `tk.Canvas`
- `App` — контроллер, управляет переключением экранов через `_clear()` + создание нового экрана

### Система сборки — `Makefile`

Собирает два артефакта:
- `chess` — консольное приложение (`main.cpp` + `table.cpp` + `figures.cpp`)
- `libchess.dylib` — разделяемая библиотека для Python (`chess_bridge.cpp` + `table.cpp` + `figures.cpp` + `ai.cpp` + `mate_searcher.cpp`)

Флаги `-fPIC` (Position Independent Code) обязательны для `.dylib` — иначе динамическая линковка не работает. Объектные файлы библиотеки компилируются в `.lo` чтобы не конфликтовать с `.o` консольного приложения.

### Ключевые OOP-концепции в проекте

| Концепция | Где применяется |
|---|---|
| Абстрактный класс | `Figure` с чистыми виртуальными методами |
| Виртуальный деструктор | `Figure::~Figure()` |
| Наследование | King, Queen, Rook, Bishop, Knight, Pawn |
| Полиморфизм | `getPseudoMoves`, `getSymbol`, `getMaterialValue` |
| Паттерн clone() | Глубокое копирование доски через `Figure*` |
| Фабричный метод | `Figure::create(type, color)` |
| mutable | `cells` в Table для const-метода `wouldLeaveInCheck` |
| Функтор | `CaptureSorter` в AI вместо лямбды |
| Opaque handle | `void*` в C API |
| Разделение ответственности | Cell хранит указатель, Table управляет памятью |
